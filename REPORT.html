Evaluation · client-side networking

The System.Net.Transport proposal as a Redis client transport

The Bedrock client surface, yanked from dmkorolev/project-bedrock and built standalone, wired into StackExchange.Redis through both of its transport seams, and run against a real redis-server. Everything here was observed by running code, not by reading the docs.

What was built

The whole Transport.Networking tree was extracted and compiled outside arcade (epoll provider; the native shim built without OpenSSL since the client path is plaintext). On top of it, a SE.Redis Tunnel uses only the proposal's public client API — NetworkTransportFactory.ConnectAsync → ConnectionContext → INetworkConnectionFeature → NetworkConnection — in two shapes:

SeamSE.Redis APIMapping
Stream (shipped)BeforeAuthenticateAsync → Stream, no socketNetworkConnection.AsStream()
Transport (experimental, SER009)ConnectTransportAsync → DuplexTransportpull→push pump over ReceiveAsync/AdvanceReceiveTo; sends via AllocateBuffer+EnqueueSend or the Output PipeWriter

Per scenario the harness runs 64 KiB and 4 MiB SET/GET round-trips, pub/sub on the second (subscription) connection, server-initiated close via CLIENT KILL with reconnect-through-the-tunnel, then awaited PINGs, pipelined INCR batches, and 32 parallel callers. Local redis-server, loopback, 4 engine workers, Release, .NET 11 — indications, not benchmarks.

1 · Things that don't work

blocker1.1 Engine disposal deadlocks forever on an abandoned connection

After a stream-mode run, NetworkTransportFactory.DisposeAsync hung indefinitely. Dump autopsy: EpollClient.StopAsync → Task.WhenAll(worker.Stopped), with the two workers that had carried connections never completing. Both connections were fully closed and drained at the native level (Closed=1, Leased=0, fd=-1 — StopConnections had closed them), but a worker's loop exits only when its connection table is empty, and the only removal is the Forget command — sent solely by the consumer's NetworkConnection.DisposeAsync, which had never run (_disposingStarted=0).

The trigger was a bug on our side — SE.Redis's PhysicalConnection.Shutdown() disposed the socket and the SER009 transport but never _ioStream, harmless for socket-backed streams but a leak for a socketless tunnel stream; fixed in our checkout. The engine behavior is still the finding: consumers with teardown bugs exist, and one leaked connection turns engine disposal into an infinite, undiagnosable hang. Suggestions: on engine dispose, forcibly reclaim connections that are natively closed but never consumer-disposed (abort + self-forget), or fail loudly after a deadline; more broadly, consider making the engine the owner of last resort, the way Kestrel's socket transport survives abandoned contexts. See also 2.4, which is how this leak class happens in practice.

blocker1.2 The direct-send admission budget turns big payloads into connection corruption

EnqueueSend/SendAsync count bytes against MaxQueuedSendBytes (default 1 MiB) and throw on overflow — "an admission limit, not a wait". For a stage-then-flush client with a fire-and-forget write model, both consequences were observed:

  • A single 4 MiB SET deterministically kills the connection. There is no way to await admission; the only options are sizing the budget for the largest conceivable flush (we passed 16 MiB) or failing.
  • Worse, the throw can land mid-batch, after part of a framed command is already queued. The connection remains "healthy" at the transport level while the protocol stream is torn — without consumer heroics (our adapter calls Abort on overflow) that is a silent desync and a timeout, not a crisp failure.

Suggestions: an awaitable admission path (EnqueueSendAsync or a WaitToSendAsync gate); a dedicated exception type; the budget on options/factory rather than only a post-connect property; and documentation of the partial-frame hazard — "a send that would exceed it throws" undersells what that does to a framed protocol.

blocker1.3 No client TLS

NetworkNativeTlsOptions is listener-only and the epoll client workers are constructed tls: false. For Redis — and most client scenarios — TLS is table stakes; today the tunnel must return null and fall back to sockets+SslStream whenever TLS is configured. Even the minimal Bedrock answer ("wrap AsStream() in SslStream yourself") deserves a stated position, because it reintroduces the Stream-adapter cost the transport seam exists to avoid — the stream-tunnel row above pays +70% ping latency and roughly half the throughput.

blocker1.4 IPv4 TCP only, and no way to ask

EpollClient.ConnectAsync throws for anything but IPv4 IPEndPoints — no IPv6, no Unix domain sockets (very common for local Redis). Combined with Bedrock's own gap #3 (no CanConnect counterpart to CanBind), a consumer cannot even ask: our tunnel re-implements the engine's constraints by hand to decide when to fall back. CanConnect(EndPoint) plus UDS support would cover the real client matrix.

2 · Things that could be improved

improve2.1 The direct send queue needs coalescing — it loses to the Output pipe by 3×

The most interesting performance result. Identical workload, syscall counts via strace -c:

EnqueueSend modeOutput pipe mode
sendto calls86,0369,587
pipelined throughput179 kop/s604 kop/s

PumpOutputCore in direct mode submits strictly one request at a time (pin → SubmitSendCore → wait completion → next) and never merges adjacent queued requests, so every flushed slice is its own wire write. The pipe path wins because the Pipe merges flushes into large segments — and only the pipe path ever sets final: true, which is what arms TCP_CORK in TcpConnection.Send; direct sends never cork. Net effect: the API's designed-for-this fire-and-forget path does 9× the syscalls and runs ~3× slower than the adapter it was meant to beat, on exactly the pipelined small-write workload a Redis client produces.

Suggestions: gather-submit queued requests (writev/sendmsg across request boundaries), or copy-merge small adjacent slices on the worker, and/or expose the cork/final hint on EnqueueSend — SE.Redis's Flush() is precisely that boundary, and the DuplexTransport contract hands it to us; we just have nowhere to put it.

Meanwhile the pipe-output result is genuinely strong: it beat the tuned socket baseline on both throughput tests (+12% pipelined, +8% parallel) at ~2 µs ping cost. The client story doesn't need new machinery to be competitive — it needs the direct path to catch up with the pipe path, or the guidance to say "clients: use Output".

improve2.2 Pull-based receive forces a re-inversion for push consumers

SE.Redis's transport contract (like SocketSet's) is push: the transport delivers spans on its own schedule, with a batch-end callback for flush coalescing. ReceiveAsync is pull, so the adapter runs a pump loop. It works, and two design choices deserve credit: the snapshot-of-everything-unconsumed result gives a natural batch boundary (snapshot-end maps to OnBatchEnd and behaves), and CompleteReceivesInline makes the pump resume on the epoll worker — effectively push-on-worker, the SocketSet shape, at exactly the right per-connection granularity. Still, each batch pays an async state-machine cycle plus cursor bookkeeping; a first-class push option (StartReceiving(handler) with a real loop-drain notification) would make inline mode cheaper and the batch boundary real rather than approximated. Measured residual on loopback: ~2–7 µs per RTT over sockets — pure adapter tax.

improve2.3 One copy is structural for pull-parsing clients

A Redis client parses out of a contiguous rolling buffer, so transport-owned pages are copied once into the parser's buffer — the same as every SE.Redis transport today, not a regression. The zero-copy story (Retain/NetworkPayload) only pays off for consumers that parse segmented sequences in place and hold leases. Worth stating which consumers the retained-lease path is for; for SE.Redis the win was never the copy — it is scheduling (2.2) and syscalls (2.1).

improve2.4 AsStream() ownership

AsStream() is deliberately non-owning, but a Stream is frequently the only handle a consumer layer gets (SE.Redis tunnels, SslStream, Bedrock's own ConnectCallback — the reason ConnectionContextStream exists). Every such consumer must hand-write an owning wrapper or leak — see 1.1, where we hit exactly this. An AsStream(ownsConnection: true) overload is cheap and removes the sharpest edge of the shipped-seam path.

improve2.5 Smaller client-surface nits

  • Blocking connect() on a pool thread (EpollClient): fine for a prototype, but a real client API needs non-blocking connect on the worker plus a connect-timeout option — today cancellation is the only control, and SE.Redis passes CancellationToken.None to tunnels; the 1.1 hang was undiagnosable partly because nothing in the dial path times out.
  • Client receive window / page sizes are env vars (NETWORKPROTO_CLIENT_LEASE_BYTES, NETWORKPROTO_CLIENT_PAGE_KB); Bedrock-API.md already says the first few should become options — agreed; they are the client analogue of the Windows pool knobs.
  • Teardown-race ergonomics: during shutdown EnqueueSend throws IOException; a bool TryEnqueueSend (or documented closed-state behavior) would avoid try/catch as control flow in every adapter's flush path.
  • CompleteReceivesInline showed no measurable latency win here (27.5 vs 26.9 µs loopback ping) — unsurprising for single-connection loopback RTT; the server numbers in Bedrock.md tell the real story. Noted only so this evaluation isn't read as contradicting them.

3 · What worked well — keep exactly as-is

  • keepThe Bedrock client surface is sufficient. NetworkTransportFactory + INetworkConnectionFeature was enough to build a complete SE.Redis transport — both seams, both send modes — with zero modifications to the prototype. DNS endpoints resolve; ConnectionClosed and the close paths behave; pub/sub's second connection and CLIENT KILL reconnects flow through the tunnel correctly.
  • keepAllocateBuffer + NetworkBufferSlice + EnqueueSend is the right shape for a stage-then-flush writer: refcounted pages, fire-and-forget with failure-by-closure, order preserved, caller releases immediately. SocketSet converged on the same shape independently — good evidence the shape is right; only the submission coalescing behind it lags (2.1).
  • keepCompleteReceivesInline as a per-connection property composes perfectly with a multiplexing client that wants parse-on-worker for data connections and default scheduling elsewhere.
  • keepEngine-per-factory anchoring maps cleanly onto "one engine, N loop threads total, regardless of topology" — thread count stays a configuration constant across any number of endpoints and multiplexers.
